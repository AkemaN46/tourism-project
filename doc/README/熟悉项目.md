# 二、接口

## 1.管理员登入与身份信息获取

1.管理员登入：POST请求，接口为/api/admin/login，校验用户名密码后会返回一个 token

2.获取身份信息：GET请求，接口为/api/admin/info，根据登入接口返回的token传入请求头中再返回管理员信息

## 2.后台数据看板

1.连通性自检：GET请求，接口为/dashboard/test，返回code/msg/时间戳

2.核心统计看板：GET请求，接口为 /dashboard/stats，返回 code / msg / data（今日收入 todayIncome、今日订单数 todayOrders、今日新增用户 todayUsers、入住率 occupancyRate、以及收入/订单/用户三条环比趋势 incomeTrend/orderTrend/userTrend，均保留 2 位小数）

3.收入趋势折线图：GET请求，接口为 /dashboard/income-trend?period=7day（可选 30day，默认 7 天），返回 code / msg / data（dates 月-日数组 + values 对应每日收入数组）

4.房型分布饼图：GET请求，接口为 /dashboard/room-type-distribution，返回 code / msg / data（[{name: 房型名, value: 数量}]，房型为空时兜底为"未知类型"）

5.最新订单列表：GET请求，接口为 /dashboard/latest-orders，返回 code / msg / data（按创建时间倒序的前 5 条订单实体）

6.待处理事项：GET请求，接口为 /dashboard/pending-tasks，返回 code / msg / data（[{type, content, time, actionUrl}]，含待支付订单 3 条 + 待审核评价 3

## 3.民宿房间收藏

1、添加收藏：POST请求，接口为 /favorite/add，请求头需带 token，Body 为 {"roomId": 1}，返回 code/msg/data，data 为收藏记录实体；已收藏时返回 data 为 true 且 msg 为"已收藏"；用户或房间不存在返回 404

2、取消收藏：POST请求，接口为 /favorite/remove，带 @Transactional 注解，请求头带 token，Body 为 {"roomId": 1}，返回 code/msg，成功为"取消收藏成功"，注意没有 data 字段

3、收藏列表：GET请求，接口为 /favorite/list，请求头带 token，返回 code/msg/data，data 为 favoriteRepository.findFavoritesByUserId 查出的收藏明细列表

4、收藏状态查询：GET请求，接口为 /favorite/check?roomId=1，请求头带 token，返回 code/msg/data，data 为布尔值，表示是否已收藏

## 4.民宿的增删改查

1、民宿列表：GET请求，接口为 /homestay/list，可带 page 默认 0、size 默认 10、keyword 可选、status 默认 1，返回 code/msg/data，data 里含 list、total、page、size，list 中每个民宿额外拼了最低价 minPrice

2、民宿详情：GET请求，接口为 /homestay/{id}，返回 code/msg/data，data 为民宿字段组成的 Map，查不到返回 404 民宿不存在

3、新增民宿：POST请求，接口为 /homestay/create，Body 直接是 Homestay 实体，返回 code/msg/data，data 为存库后的实体，异常返回 500 加异常信息

4、编辑民宿：PUT请求，接口为 /homestay/update/{id}，Body 直接是 Homestay 实体，返回 code/msg，成功为编辑成功，查不到返回 404

5、删除民宿：DELETE请求，接口为 /homestay/delete/{id}，先按 homestayId 删房型再删民宿，返回 code/msg，成功为删除成功

6、切换状态：PUT请求，接口为 /homestay/toggleStatus/{id}，把 status 在 1 和 0 之间翻转，返回 code/msg/data，data 为切换后的状态值

## 5.旅游资讯模块

1、资讯列表：GET请求，接口为 /news/list，可带 page 默认 0、size 默认 10、title 可选（标题模糊查）、categoryId 可选、status 可选，排序规则是先按 sortOrder 降序再按 id 降序，返回 code/msg/data，data 含 list、total、page、size

2、资讯详情：GET请求，接口为 /news/{id}，返回 code/msg/data，data 是资讯的全部字段，查不到返回 404 资讯不存在；另外当这条资讯 status 为 1 时，会顺手把 viewCount 加一并存

3、创建资讯：POST请求，接口为 /news/create，Body 是 News 实体，viewCount 和 sortOrder 为空时会补默认值 0，返回 code/msg/data，data 是创建后的资讯

4、更新资讯：PUT请求，接口为 /news/{id}，Body 是 News 实体，会逐字段覆盖标题、副标题、分类、作者、封面图、正文、状态、排序，返回 code/msg/data，data 是更新后的资讯，查不到返回 404

5、删除资讯：DELETE请求，接口为 /news/{id}，返回 code/msg，成功为删除成功，查不到返回 404

## 6.订单模块

1、创建订单：POST请求，接口为 /order/create，请求头可带 Authorization 或 token，Body 是 Map，需含 roomId、roomName、roomImage、checkInDate、checkOutDate、nights、price、totalAmount、realAmount、contactName、contactPhone、remark。日期按 yyyy-MM-dd 解析，用户 ID 从 toke 里取，状态固定置为 0 待支付，订单号用 ORDER 加当前毫秒数生成。返回 code/msg/data，未登录返回 401，data 是保存后的订单

2、批量创建订单：POST请求，接口为 /order/batch-create，Body 是 {"orders": [ 多条订单对象 ]}，循环里逐条构建订单，状态直接置为 1 已支付，并写入 paymentTime 和支付方式 wxpay-微信支付，订单号是 ORDER 加毫秒数再加一个随机数。订单为空返回 400，返回 code/msg/data，data 是保存后的订单数组

3、订单列表：GET请求，接口为 /order/list，可带 page 默认 0、size 默认 10、orderNo 可选（模糊查）、contactName 可选（模糊查）、status 可选，按创建时间倒序。权限规则是管理员能看全部订单，普通用户只能看自己的，返回 code/msg/data，data 含 list、total、page、size

4、订单详情：GET请求，接口为 /order/{id}，返回 code/msg/data，data 是订单实体。权限判断是管理员 token 可访问任意订单，普通用户只能访问 order.userId 与自己对得上的订单，不匹配返回 403 无权访问此订单，订单不存在返回 404

5、更新订单状态：PUT请求，接口为 /order/{id}/status，状态可以放 URL 参数 status，也可以放 Body 的 status 字段，两者都没有返回 400。权限同样是管理员任意、普通用户限本人，越权返回 403。普通用户还要过一层状态机校验。状态改成 1 会写 paymentTime，改成 3 会写 completedTime，改成 4 会把取消原因写成管理员取消。返回 code/msg/data，data 是更新后的订单

6、取消订单：PUT请求，接口为 /order/{id}/cancel，Body 可选，可带 {"reason": "取消原因"}，不传则记为用户取消。只有状态为 0、1、2 的订单可以取消，其余返回 400 当前状态的订单不能取消，取消后状态置为 4。返回 code/msg/data，data 是取消后的订单

## 7.房源个性化推荐模块

1、房源推荐：GET请求，接口为 /recommend/rooms，请求头可带 Authorization（支持 Bearer 前缀）或 token，都可选；可带 size 默认 8、上限 20，可带 alpha 用于调整协同与内容的配比，默认 0.6，会被夹在 0 到 1 之间。返回 code/msg/data，data 含 list 和 total，list 里是房源展示对象

这个接口有四种返回分支，靠 msg 区分：

一是库里没有在架房源，msg 为暂无在架房源，list 返回空数组
二是没解析出用户 ID（未登录或 token 无效），msg 为未登录用户，返回热门房源，按全局热度倒序取前 size 条
三是登录了但没有任何订单和收藏记录，msg 为用户行为较少，返回热门房源，逻辑同上
四是正常推荐，msg 为获取推荐成功

## 8.评论模块

评价状态用数字表示：0 待审核、1 已通过、2 未通过。

1、评价列表：GET请求，接口为 /review/list，可带 page 默认 0、size 默认 10、roomName 可选（按房型名称模糊查，内部会 join 房间表并按小写比对）、status 可选，返回 code/msg/data，data 含 list、total、page、size

2、我的评价：GET请求，接口为 /review/user，请求头可带 Authorization 或 token，可带 page 默认 0、size 默认 10、status 可选，按 userId 过滤，未登录返回 401 用户未登录，返回结构与列表一致

3、提交评价：POST请求，接口为 /review/create，请求头带 token，Body 需含 orderId、roomId、rating、content，images 可选，返回 code/msg。评分必须在 1 到 5 之间否则返回 400；订单不存在返回 404；订单不属于当前用户返回 403 无权评价此订单；同一订单重复评价返回 400 此订单已评价过。提交成功后评价状态为 0 待审核，同时把订单的 reviewed 字段置为true

4、删除评价：DELETE请求，接口为 /review/{id}/delete，请求头带 token，只有评价作者本人能删，越权返回 403，评价不存在返回 404，成功返回 code/msg

5、修改评价：PUT请求，接口为 /review/{id}/update，请求头带 token，Body 需含 rating、content，images 可选，返回 code/msg。只有状态为 2 未通过的评价才能编辑，否则返回 400 只有未通过的评价才能编辑；改完后状态会重新置回 0 待审核

6、评价详情：GET请求，接口为 /review/{id}，无需登录，返回 code/msg/data，data 含 id、roomId、userId、roomName、userName、userAvatar、rating、content、status、createdAt、replyContent、images，查不到返回 404

7、评价详情增强版：GET请求，接口为 /review/{id}/detail，无需登录，返回字段更全一些，比上一条多了 orderId、roomImage，并把用户信息换成了 nickname、avatarUrl、gender，返回 code/msg/data

8、审核通过：POST请求，接口为 /review/{id}/approve，请求头需带管理员 token（admin_token 开头），非管理员返回 403 无权进行此操作，审核后状态置为 1，返回 code/msg

9、审核拒绝：POST请求，接口为 /review/{id}/reject，请求头需带管理员 token，Body 可带 {"reason": "拒绝原因"}，会把原因写进 replyContent 并记录 replyTime，状态置为 2，返回 code/msg

出参的统一约定：roomName 查不到时兜底为未知民宿；用户名查不到时兜底为匿名用户、头像为空字符串；images 在为空或为字符串 [] 时返回空数组。

## 10.购物车模块

1、加入购物车：POST请求，接口为 /cart/add，请求头必须带 token，Body 需含 roomId、checkInDate、checkOutDate，返回 code/msg/data。日期用 java.sql.Date.valueOf 解析，要求 YYYY-MM-DD 格式，格式不对返回 400 日期格式错误；用户不存在或房间不存在返回 404；如果同一用户、同一房间、同一入住日期已经在购物车里，返回 200 加 msg 已在购物车中，data 是那条已有记录；否则新建一条并返回添加成功和保存后的记录

## 11.文件上传模块

1、图片上传：POST请求，接口为 /upload/image，表单参数名为 file，类型必须是文件。返回 code/msg/data，data 里同时给了 url 和 imageUrl 两个字段，值相同，都是 /images/ 加上文件名，前者是前端在用的字段名，后者是为了兼容旧版本

整个方法的处理顺序是五步：

第一步校验文件是否为空，为空返回 400 请选择要上传的图片。
第二步校验文件名后缀，没有后缀名返回 400 无效的图片文件；后缀只允许 jpg、png、webp 三种，大小写不敏感，其他一律返回 400 仅支持jpg、png、webp格式图片；文件大小上限 5MB，超出返回 400 图片大小不能超过5MB。
第三步确认上传目录存在，不存在就调用 mkdirs 逐级创建，创建失败返回 500 无法创建上传目录。
第四步用 UUID 加原后缀生成文件名，避免重名覆盖。
第五步 transferTo 落盘，成功后拼出 /images/文件名 作为访问地址返回。落盘过程中的异常会打印堆栈并返回 500。

几个关键约定：

上传目录由类常量 UPLOAD_PATH 写死，源码里是 D:\thesis\system_project\backend\uploads\images\，也就是 Windows 下 D 盘的 thesis 项目目录，注释里还专门说明这是为了兼容中文路径和 Windows 转义。这个目录和当前工程所在的 D:\Projects\tourism-project\system_project 并不是同一个位置，实际部署时按真实存放位置调整这个常量即可。

返回的是相对路径 /images/xxx，而不是完整 URL，注释里写明要和 WebMvcConfig 里的资源映射保持一致。这也解释了为什么前面几个 Controller 里都要自己拼 http://localhost:8082/ 前缀——上传时只存相对路径，展示时由各业务接口补全域名。

上传接口本身不校验登录身份，也不校验 token，任何能访问到接口的请求都能传文件。

## 12.用户模块

1、简易登录：POST请求，接口为 /user/login，表单参数 code，返回 code/msg/data，data 里是 mock_token_ 加当前毫秒数。这个接口是简化版，没有真正去微信换取 openid

2、微信授权登录：POST请求，接口为 /user/wxlogin，Body 为 {"code": "前端 wx.login 拿到的 code"}，返回 code/msg/data。缺少 code 返回 400 缺少微信 code 参数；微信接口调用失败返回 500 微信授权失败，请重试；成功时 data 含三项：token、userId、userInfo（里面有 id、nickname、avatarUrl）。流程是拿 code 调微信的 jscode2session 换 openid 和 session_key，然后用 openid 查库，查不到就自动注册一个用户，昵称规则是微信用户_ 加当前毫秒数取模 10000，状态置为 1，最后签发自定义 token

3、获取用户信息：GET请求，接口为 /user/info，请求头必须带 token，返回 code/msg/data，data 是完整的 User 实体。用户 ID 取自 token 分段后的倒数第二段，token 段数小于 3 返回401 无效的令牌，查不到用户返回 404

4、更新用户资料：POST请求，接口为 /user/update，请求头必须带 token，Body 是 UserUpdateDTO，返回 code/msg/data，data 是更新后的用户。支持改的字段有 nickname、avatarUrl、gender、birthday、phone、email，逐个判空，传了才更新；birthday 按 yyyy-MM-dd 解析，格式不对返回 400 生日格式不正确。这里取用户 ID 用的是 token 分段后的最后一段

5、用户列表：GET请求，接口为 /user/list，可带 page 默认 0、size 默认 10，另外还接收 nickname、phone、status 三个可选参数；实际查询走的是 findAll 分页。返回 code/msg/data，data 含 list、total、page、size，list 里每个用户在原有字段（id、nickname、avatarUrl、phone、email、gender、birthday、status、createdAt）基础上额外带一个 orderCount，取的是该用户的有效订单数，统计时排除了已取消和已退款

6、用户历史订单：GET请求，接口为 /user/{userId}/orders，可带 page 默认 0、size 默认 10，返回 code/msg/data，data 含 list、total、page、size。会先校验用户是否存在，不存在返回 404；订单按创建时间倒序，并且排除状态为 4 和 5 的订单，也就是已取消和已退款

# 三、实体类（entity 包）

实体类位于 backend/src/main/java/com/homestay/xiaozhu/entity。项目共有 10 个 JPA 实体，分别对应 users、admins、homestay、rooms、room_status、orders、reviews、favorites、shopping_cart、news 表；另外还有 UserUpdateDTO 和 JwtUtil 两个辅助类。

项目没有使用 JPA 的 @OneToMany、@ManyToOne 等对象关系映射，实体之间主要通过 userId、roomId、homestayId、orderId 等 Long 类型字段关联。跨表展示数据由 Controller 或 Repository 查询后组装。

## 1. 核心实体和业务关系

| 实体 | 对应表 | 主要作用 | 关键字段或关系 |
| --- | --- | --- | --- |
| User | users | 小程序用户 | openid 唯一；关联订单、评价、收藏、购物车 |
| Admin | admins | 后台管理员 | username 唯一；与 User 是两套独立账号体系 |
| Homestay | homestay | 民宿信息 | 一个民宿包含多个房型 |
| Room | rooms | 房型和价格库存 | 关联民宿，并被房态、订单、评价、收藏、购物车引用 |
| RoomStatus | room_status | 每日房态 | roomId + date 唯一，保存每日价格、库存、可预订状态 |
| Order | orders | 用户预订记录 | 关联用户和房型，包含金额、入住日期和状态 |
| Review | reviews | 用户评价 | 关联用户、订单和房型；同一订单只能评价一次 |
| Favorite | favorites | 用户收藏 | userId + roomId 唯一的关联表 |
| ShoppingCart | shopping_cart | 用户购物车 | 关联用户和房型，并保存入住、离店日期 |
| News | news | 旅游资讯 | 通过 categoryId 关联分类，但项目中没有分类实体 |

## 2. 需要重点理解的三个对象

### Room：业务中心

Room 是房源业务的中心，向上属于 Homestay，向下关联 RoomStatus、Order、Review、Favorite 和 ShoppingCart。房型的上下架、价格、库存会同时影响房源展示、日历、下单和推荐。

### Order：核心状态对象

订单状态约定如下：

| 状态值 | 含义 |
| --- | --- |
| 0 | 待支付 |
| 1 | 已支付 |
| 2 | 入住中 |
| 3 | 已完成 |
| 4 | 已取消 |
| 5 | 已退款 |

订单会保存 roomName、roomImage、price 等下单时的快照，因此房型后续改名或改价不会改变历史订单。

### Review：订单后的业务对象

提交评价前需要校验订单存在、订单属于当前用户、订单尚未评价。评价创建后为待审核状态，管理员可以通过或拒绝；被拒绝的评价可以修改后重新进入待审核状态。

## 3. 实体层测试关注点

1. 关联 ID 不存在时，接口是否返回正确的 404 或业务错误。
2. 唯一字段重复时，是否被接口校验或数据库唯一键拦截。
3. 订单金额、入住日期、离店日期和晚数是否一致。
4. 订单状态变化时，支付时间、完成时间和取消原因是否同步更新。
5. 删除民宿或房型时，关联的房态、收藏、购物车、订单和评价分别如何处理。
6. 实体字段与数据库真实字段不一致时，是否产生数据丢失或接口字段缺失。

## 4. 两个辅助类

- UserUpdateDTO：只用于接收用户资料更新请求，不对应数据库表。
- JwtUtil：负责 Token 的生成和校验。当前 Token 使用 HS256，载荷包含用户 ID，有效期为 24 小时。测试时要覆盖 Token 缺失、过期、格式错误和用户越权。

# 四、数据访问层（repository 包）

Repository 位于 backend/src/main/java/com/homestay/xiaozhu/repository。10 个 Repository 都是接口，继承 JpaRepository，由 Spring Data JPA 自动生成实现。

## 1. 访问层的基本职责

Repository 主要负责：

- 按 ID 查询、保存、删除和判断存在。
- 分页查询和排序。
- 根据接口方法名生成简单条件查询。
- 使用 JPQL 或原生 SQL 完成统计和联表查询。
- 为 Controller 提供数据库结果，业务判断主要仍在 Controller 中完成。

常用基础方法包括 save、findById、findAll、findAll(Pageable)、deleteById、existsById、count。列表接口通常通过 PageRequest.of(page, size) 实现分页。

## 2. 三类查询方式

| 查询方式 | 适合场景 | 示例 |
| --- | --- | --- |
| 派生查询 | 条件简单、方法名可以表达 | findByOpenid、findByUserIdAndRoomId |
| JPQL | 统计、分组和实体字段查询 | 今日收入、房型分布、有效订单数 |
| 原生 SQL | 需要联表或使用 MySQL 函数 | 收藏列表、购物车列表 |

Homestay、Room、Order、Review、News 还实现了 JpaSpecificationExecutor，用于处理关键词、状态、价格区间等可选条件较多的分页查询。

## 3. 各 Repository 只需要记住什么

| Repository | 核心用途 | 测试重点 |
| --- | --- | --- |
| UserRepository | openid 查用户、统计新增用户 | 微信登录自动注册、重复 openid、统计日期 |
| AdminRepository | 按用户名查询管理员 | 当前登录接口是否真正使用数据库账号 |
| HomestayRepository | 民宿分页、保存和删除 | 关键词、状态、分页、级联删除 |
| RoomRepository | 房型查询、最低价、房型分布、推荐候选 | 上下架、最低价是否包含下架房型 |
| RoomStatusRepository | 查询日期范围内的房态 | 起止日期、缺失日期补默认值、重复日期 |
| OrderRepository | 订单列表、状态统计、推荐行为数据 | 状态口径、金额统计、分页和越权 |
| ReviewRepository | 评价列表、审核、重复评价校验 | 状态筛选、订单唯一评价、审核权限 |
| FavoriteRepository | 收藏增删查和推荐热度 | 重复收藏、用户归属、级联删除 |
| ShoppingCartRepository | 购物车增删查和联表展示 | 日期合法性、记录归属、重复加购 |
| NewsRepository | 资讯筛选、排序和分页 | 发布状态、排序规则、浏览量 |

## 4. 数据访问层当前值得记录的问题

1. Controller 直接注入 Repository，Service 层没有统一参与业务处理，后期维护和单元测试成本较高。
2. AdminRepository、部分派生查询和部分统计方法目前没有调用点，属于预留或遗留代码。
3. 部分查询使用 DATE(created_at) 等函数，数据量大时可能无法充分利用索引。
4. 推荐接口一次性查询全部在架房源，数据量增长后需要关注内存和响应时间。
5. 用户列表为每个用户额外统计有效订单数，可能形成 N+1 查询。
6. 收藏和购物车的原生 SQL 依赖 MySQL 函数及字段别名，修改 SQL 时要同步检查前端。
7. 删除民宿时先删除房型再删除民宿，事务边界需要通过接口测试验证。
8. 看板中的今日订单数、今日收入和入住率使用的统计口径不完全一致。

## 5. Repository 层测试方法

测试 Repository 不需要逐个背方法名，可以围绕下面五类问题设计用例：

1. 条件查询：关键词、状态、价格区间和日期范围是否正确。
2. 分页排序：页码、每页数量、总数、空页和排序方向是否正确。
3. 关联查询：返回的房型名、封面图、晚数等联表字段是否完整。
4. 数据一致性：新增、修改、删除后再次查询是否得到正确结果。
5. 边界和异常：空参数、非法日期、重复数据、不存在的关联 ID 和数据库约束异常。

建议的阅读顺序是：

~~~
Controller 接口
  -> Controller 调用的 Repository 方法
  -> 对应实体字段
  -> 数据库表结构和索引
  -> 再回到接口设计测试用例
~~~

这样可以避免把大量时间花在暂时没有调用点的 Repository 方法上。
# 五、Controller 层与后端调用链

## 1. 后端整体调用方式

这个项目的后端采用 Spring Boot + Spring Data JPA。请求一般直接进入 Controller，再由 Controller 调用 Repository 完成查询或保存，Service 层没有被所有模块统一使用。

典型调用链如下：

```text
前端页面
  -> request.js / wx.request
  -> Controller
  -> Repository
  -> MySQL
  -> Controller 组装统一返回值
  -> 前端渲染
```

阅读代码时，建议从接口入口进入，而不是从实体类开始逐行阅读。

## 2. Controller 职责

| Controller | 主要功能 | 优先关注点 |
| --- | --- | --- |
| AdminController | 管理员登录、管理员信息 | 登录凭证是否真实校验、Token 格式 |
| DashboardController | 数据看板和统计图 | 统计口径、日期范围、空数据 |
| HomestayController | 民宿增删改查 | 分页、状态切换、级联删除 |
| RoomController | 房型和房态 | 价格、库存、日期、上下架 |
| OrderController | 订单创建、查询、取消、状态流转 | 权限和订单状态机 |
| ReviewController | 评价提交、修改、审核 | 用户归属、重复评价、审核状态 |
| FavoriteController | 收藏和取消收藏 | 重复收藏、用户身份 |
| ShoppingCartController | 购物车增删查 | 日期合法性、记录归属 |
| NewsController | 旅游资讯管理 | 发布状态、排序、浏览量 |
| UserController | 微信登录、用户资料、用户订单 | code 一次性、Token、隐私字段 |
| UploadController | 图片上传 | 文件类型、大小、路径和未授权上传 |
| RecommendationController | 个性化房源推荐 | 未登录兜底、数据量、推荐结果 |

## 3. 统一返回和异常处理

大多数接口返回 `code`、`msg`、`data` 三个字段。测试时不能只看 HTTP 状态码，还要检查业务 `code` 和 `msg`。

重点检查：

1. HTTP 200 但业务 code 为 400、401、403 或 500。
2. 成功响应缺少 data，或者 data 类型与前端预期不一致。
3. 资源不存在时是否返回 404，而不是空对象或 500。
4. 参数错误、未登录、无权限和服务器异常是否能够区分。

`GlobalExceptionHandler` 是后端异常的统一出口。遇到接口返回 500 时，应同时查看后端日志，不能只根据前端提示判断原因。

# 七、核心业务流程

## 1. 管理员流程

```text
管理员登录
  -> 保存 admin token
  -> 进入数据看板
  -> 管理民宿
  -> 管理房型和房态
  -> 查看订单
  -> 审核评价
  -> 发布旅游资讯
```

每个流程都需要验证正常成功、参数为空、资源不存在、重复操作、Token 缺失和普通用户越权。

## 2. 普通用户流程

```text
微信登录
  -> 首页浏览房源或资讯
  -> 查看房型详情和评价
  -> 收藏或加入购物车
  -> 创建订单
  -> 查询、取消或更新订单
  -> 提交评价
  -> 查看个人资料、收藏和历史订单
```

订单是最重要的主流程，建议先画出状态变化：

```text
待支付(0) -> 已支付(1) -> 入住中(2) -> 已完成(3)
       \\-> 已取消(4)
```

测试时重点验证非法跳转，例如已完成订单再次支付、已取消订单再次入住、普通用户修改其他人的订单。

# 八、项目熟悉和测试执行顺序

## 第 1 步：完成运行确认

1. 启动 MySQL、后端和后台管理端。
2. 确认后台地址为 `http://localhost:9532`，后端地址为 `http://localhost:8082`。
3. 用管理员账号登录后台。
4. 在微信开发者工具中编译小程序，完成微信登录。
5. 记录启动日志、浏览器控制台和小程序 Console 中的异常。

## 第 2 步：建立模块和接口清单

以“模块—页面—接口—数据表—权限”为维度整理，不必立即阅读所有代码。

| 模块 | 页面 | 接口 | 主要数据表 | 关键风险 |
| --- | --- | --- | --- | --- |
| 登录 | 小程序登录页 | `/user/wxlogin` | users | code 一次性、AppID 和密钥匹配 |

## 第 3 步：手工冒烟测试

先验证主链路是否可以走通：登录 → 浏览房源 → 查看详情 → 加购或下单 → 查询订单 → 取消订单或完成评价。主流程稳定后再补异常场景。

## 第 4 步：接口测试

使用 Postman 或 Apifox 为每个模块建立请求集合，至少覆盖正常请求、必填参数缺失、参数类型错误、边界值、Token 缺失或失效、资源不存在、重复提交和越权访问。

接口断言建议同时断言状态码、响应字段、数据类型、错误提示和数据库变化。

## 第 5 步：数据库校验

写操作完成后，用 SQL 验证数据是否正确落库；删除、取消、审核和更新状态尤其要检查操作前后的数据。

重点校验订单金额、订单状态、支付时间、评价状态、浏览量、收藏唯一性、购物车唯一性和级联删除。

## 第 6 步：前端 UI、兼容性和性能测试

后台重点测试分页、搜索、表单校验、上传、弹窗、状态切换和刷新后数据是否保持。小程序重点测试不同屏幕尺寸、慢网络、重复点击、返回页面、未登录访问、图片加载失败和日期选择。

可以使用 JMeter 对房源列表、订单列表、看板统计和推荐接口进行压测，观察响应时间、错误率、数据库连接数和慢查询。

# 九、自动化测试落地建议

建议使用 `pytest + requests` 编写接口自动化，使用 Playwright 测试后台登录、房源管理和订单查询。先自动化稳定的主流程，再覆盖异常场景。

推荐优先自动化：

1. 管理员登录和 Token 校验。
2. 房源列表分页、搜索和详情。
3. 订单创建、查询和取消。
4. 评价提交、重复评价和审核。
5. 用户越权访问其他用户数据。

# 十、当前代码中值得记录的风险

1. 管理员登录接口目前使用固定账号逻辑，`AdminRepository` 和管理员 Service 没有真正接入登录流程。
2. 上传接口没有登录校验，任何能访问接口的请求都可能上传图片。
3. 购物车只校验日期格式，没有校验离店日期必须晚于入住日期。
4. 删除民宿时先删除房型，事务边界需要重点验证。
5. 看板中的订单数、收入和入住率统计口径不完全一致。
6. 部分查询存在未调用方法、冗余查询或潜在类型问题，属于可维护性风险。
7. 多个列表接口在 Controller 中直接拼接查询条件，参数组合多，适合做组合测试。
8. 微信 AppSecret 属于敏感配置，不应写入 README、学习笔记或公共代码仓库。
