# 汐岸小筑民宿平台 V1.1 开发迭代说明（2026-09-18 修订）

**发布日期：** 2026-09-18  
**面向对象：** 小程序、管理后台、后端开发与测试人员  
**版本目标：** 收敛为“找民宿—选房型—预订—查看订单”的核心闭环，并修复当前版本中的安全、订单与数据一致性问题。

## 1. 本次产品决策

1. **重构民宿浏览层级。** 民宿是一级对象，房型是民宿下的二级对象；不得再把房型列表命名或呈现为“民宿列表”。
2. **民宿列表恢复为一次性列表加载。** 取消小程序端的分页、触底加载和“加载更多”交互；当前已上架民宿必须在首次进入“民宿”页时直接显示。后台接口仍可保留分页参数作为保护措施，但小程序不得依赖分页状态显示数据。
3. **房型、收藏和购物车等用户端列表同样取消分页交互。** 恢复一次性请求并渲染当前数据；管理后台的列表分页可继续保留。
4. **“为你推荐”增加查看更多。** 该入口进入全局房型列表，不改变“民宿 → 民宿详情 → 该民宿房型”的主浏览链路。

## 2. 小程序信息架构与页面改版

### 2.2 民宿—房型的正确浏览路径

```text
首页搜索
  → 综合搜索结果（民宿、房型）
  → 点击民宿：民宿详情 → 该民宿房型列表
  → 点击房型：房型详情

底部“民宿”
  → 民宿列表
  → 点击某一家民宿
  → 该民宿详情（基本信息）
  → 该民宿的房型列表
  → 房型详情
  → 选择日期并下单
```

| 页面 | 设计要求 | 接口与数据要求 |
| --- | --- | --- |
| 民宿列表（新增或改造为一级页） | 页面标题为“民宿列表”。卡片至少展示封面、民宿名称、地址/区域、评分（有则展示）、起订价（有则展示）。只展示上架民宿。支持关键词搜索；**首次进入直接完整展示当前结果，不显示分页、触底加载或加载更多。** | 查询对象为 `Homestay`，服务端只返回 `status=上架` 的记录；小程序固定一次性取得当前列表（单次请求上限 50 条），并将 `data.list` 直接绑定到页面。 |
| 民宿详情（新增） | 展示封面、名称、地址、电话、简介、设施/标签（如有），并提供“查看房型”主按钮；页面可直接展示该民宿的房型摘要。 | 根据民宿 ID 查询；不存在或已下架时返回明确提示，不返回其房型。 |
| 房型列表（改造现有 `pages/room/list`） | 页面标题为“{民宿名称} · 房型”；头部固定展示所属民宿名称和封面/地址摘要。每张房型卡片同时显示“所属民宿：{民宿名称}”，避免用户失去上下文。用户端不显示分页或加载更多。 | 民宿详情进入时必须带 `homestayId`；后端按该民宿过滤，仅返回“民宿上架且房型上架且可订”的房型。 |
| 首页“为你推荐” | **保留为房型推荐。** 卡片展示房型封面、房型名称、所属民宿名称、价格/晚和核心标签；点击进入房型详情。标题右侧新增“查看更多 >”，点击进入全局房型列表。 | 推荐接口按房型维度返回，并同时返回 `homestayId`、`homestayName`；仅返回所属民宿上架、房型上架且可订的房型。查看更多进入 `pages/room/list?scope=all`。 |
| 全局房型列表 | 仅由“为你推荐 → 查看更多”进入，标题为“全部房型”。每张卡片必须展示所属民宿；用户端不显示分页或加载更多。 | `scope=all` 时返回全部可售房型；不得与带 `homestayId` 的民宿内房型列表混用。 |
| 首页搜索 | 同时搜索民宿和房型。搜索结果页默认按“民宿”“房型”两个分组展示，并可按“全部 / 民宿 / 房型”筛选；民宿结果进入民宿详情，房型结果进入房型详情。 | 关键词匹配民宿名称、区域/地址及房型名称；房型结果必须附带所属民宿名称。用户端每个分组一次性返回当前结果，不做分页交互。 |

### 2.3 小程序路由实现约束

- 底部“民宿”使用新的民宿列表页；原房型列表不再作为 tabBar 页面，允许携带 `homestayId` 参数进入。
- 底部“订单”使用 `pages/order/list` 作为 tabBar 页面。首页、下单成功等跳转订单页时使用 `switchTab`；订单详情仍使用 `navigateTo`。
- 删除资讯页面后，同步删除首页 `loadNews`、`goToNewsList`、`goToNewsDetail`、资讯 tabBar 配置与相关静态资源引用。
- 首页搜索不得只跳转民宿列表或全局房型列表，应进入综合搜索结果页；推荐区保留现有房型详情跳转逻辑，并补全所属民宿名称展示。
- “为你推荐”的“查看更多”通过 `navigateTo` 进入 `pages/room/list?scope=all`；民宿内房型仍使用 `pages/room/list?homestayId={id}`。两个入口的标题、请求参数和空态提示必须不同。
- 民宿列表的请求成功后必须直接把 `res.data.list` 赋值给页面 `list`。响应结构异常、网络失败或图片加载失败不得静默展示“暂无已上架民宿”：前两者显示“加载失败，点击重试”，图片失败仅替换为占位图，卡片仍显示。
- 删除用户端 `page`、`hasMore`、`onReachBottom`、触底追加及“加载更多”相关状态和 UI；刷新操作只重新请求并替换完整列表。
- 页面标题、按钮文案和注释须统一使用“民宿”“房型”。当前把房型页命名为“民宿列表”的文案必须全部修正。

## 4. 输入边界与后端校验规则

下列规则为本次明确的产品上限。前端需通过 `maxlength`、日期组件和即时提示限制；后端使用 DTO + Bean Validation 或等价校验实现同一规则。任何校验失败均返回业务 code=400 和可读错误信息，不得抛出 500。

| 场景/字段 | 规则 |
| --- | --- |
| 民宿名称 | 去首尾空格后 2–50 字符。 |
| 民宿地址 | 5–120 字符。 |
| 民宿简介 | 最多 500 字符。 |
| 房型名称 | 去首尾空格后 2–50 字符。 |
| 房型简介 | 最多 500 字符。 |
| 销售价/划线价 | 大于 0 且不超过 100,00 元，保留两位小数；划线价不得低于销售价。 |
| 库存 | 整数 0–999；库存为 0 时不可预订。 |
| 联系人 | 去首尾空格后 2–20 字符，仅中文、英文字母和中间空格。 |
| 手机号 | 中国大陆 11 位手机号码。 |
| 订单备注 | 最多 200 字符；小程序下单页和批量下单页均增加 `maxlength="200"`。 |
| 评价内容 | 1–500 字符；后端同样限制，不能只依赖小程序现有 `maxlength="500"`。 |
| 入住/离店日期 | 入住日期不得早于今天，离店日期必须晚于入住日期；入住日期不得晚于未来 365 天；每笔最长 60 晚。 |
| 购物车批量结算 | 单次最多提交 10 个房型；每项均重新校验日期、状态、库存和金额。 |
| 列表加载 | 小程序端不使用分页交互，民宿、房型、收藏、购物车和搜索分组均一次性请求、一次性渲染当前结果；接口如保留 `page`、`size` 参数，服务端仍须限制 `page >= 1`、`size <= 50`，避免无边界查询。管理后台可继续使用分页。 |
| 图片上传 | 仅 JPG、PNG、WEBP；单文件 5 MB 以内；文件名使用服务端 UUID；校验 MIME 类型和扩展名；仅管理员可上传。文件保存目录固定为本项目后端的 `system_project/backend/uploads/images`，不得创建项目外目录。 |

## 5. 后端实现底线

1. 为登录用户与管理员分别建立统一鉴权拦截器/过滤器，不允许 Controller 通过读取前端传入的 `userId` 决定数据归属。
2. 下单接口只接收必要输入：`roomId`、入住日期、离店日期、联系人、手机号、备注。订单名称、图片、价格、金额、状态、用户 ID 和订单号均由服务端生成。
3. 下单、批量下单和状态变更使用事务；任一步失败应整体回滚。批量下单不得无条件清空购物车。
4. 将 Controller 中直接接收 `Map<String, Object>` 的关键接口改为明确 DTO，统一进行参数校验和异常转换。
5. 所有资源不存在、无权限、状态不允许、参数非法的情况分别返回 404、401/403、409、400；不得用 HTTP 200 + code=500 表示可预期的业务失败。
6. 删除或下架民宿、房型前校验关联订单的处理规则；至少不能让前台继续售卖，历史订单仍需保留快照可查。
7. 图片上传目录通过应用配置项管理，开发环境默认解析为 `system_project/backend/uploads/images`。删除 `UploadController` 中硬编码的个人目录（当前为 `D:\\thesis\\...`）；目录不存在时只能在上述项目内创建。`/images/**` 静态映射必须指向同一目录，接口返回 `/images/{UUID}.{suffix}` 后可直接访问。
